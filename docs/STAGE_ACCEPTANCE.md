# 各阶段验收方案

本方案验证[开发需求介绍](DEVELOPMENT_REQUIREMENTS.md)中的 R1–R8，实施顺序参见[开发方案](DEVELOPMENT_PLAN.md)。每项结果记录为“通过 / 失败 / 阻塞 / 未执行”，不得把计划、TODO 或仅能解析依赖记为“通过”。当前仓库没有 `tests/`。本机已验证 `cjc/cjpm` 1.1.3 和 TCP 最小探针；已配置匹配的 stdx 1.1.3.1，`cjpm check` 和 `cjpm build` 已通过；M0 的 JSON、密码输入和密码派生 API 探针仍待完成，M0 尚未通过。下列项目验收用例均未执行。

## 通用记录格式

每个阶段保留执行日期、负责人、机器与系统、SDK/stdx 版本、`cjc -v` 的 Target、测试命令、输入、实际输出、通过/失败结论和问题编号。命令行、服务端日志和客户端截图可作证据，但日志与截图不得包含真实密码。出现失败时写出最短复现步骤；修复后重新跑受影响阶段及其后续阶段。

| 阶段 | 验收主题 | 进入条件 | 通过后才可进入 |
|---|---|---|---|
| M0 | 环境和 API 校准 | 仓库可读取，确定演示操作系统 | M1 |
| M1 | 协议与框架 | M0 官方探针通过 | M2 |
| M2 | 账号与登录 | M1 构建和协议测试通过 | M3 |
| M3 | 公共聊天与私信 | M2 登录闭环通过 | M4 |
| M4 | 健壮性、局域网演示与交付 | M3 核心聊天通过 | 课程交付 |
| M5 | 文件/图片选做 | M4 已通过 | 单独展示，不影响核心交付 |

## M0：环境和 API 校准

**检查步骤**

1. 在计划演示的 Linux 或 Windows 机器上安装仓颉 SDK；先加载对应的 `envsetup.sh` 或 `envsetup.ps1`，再运行 `cjc -v`、`cjpm --version`，记录版本与 Target。
2. 下载匹配版本的 stdx，核对 `package.json` 中的 `cjc_version`，确认实际 `dynamic/stdx` 目录及 `cjc -v` 的 Target，配置对应平台的 `path-option`；分别在计划使用的系统上运行 `cjpm check`。
3. 分别用所选 SDK 的官方 TCP 示例和对应 stdx JSON 示例编译、运行；TCP 示例要实际收发一段包含中文的内容。
4. 确认 `TcpSocket` 的导入包名、JSON 对象的构造/编解码 API、隐藏密码输入方式、安全随机源及可用密码派生库，记录可执行的最小探针和结论。

**通过标准**：工具命令可用、两个探针均运行成功、版本/Target/库路径和 API 选择有记录。本工程此时仍可有 TODO，不能要求聊天已运行。**证据**：版本输出、探针源码及运行结果、库目录记录。

## M1：协议与框架

**检查步骤**

1. 确认入口参数、网络与 JSON 导入在组内选定 SDK 上仍可编译；运行 `cjpm check`、`cjpm build`。
2. 实现并测试 `encode/decode/LineReader.read/writeLine`：一个 JSON 对象一帧，写出追加一个 LF，接收兼容 CRLF；空行忽略。
3. 测试 TCP 一次收到半行、两行粘在一次读取中、中文/emoji 跨底层读取边界、非法 UTF-8、畸形 JSON、字段缺失、错误字段类型，以及 64 KiB 边界和超限。
4. 测试用户名 3–16 位规则、空白正文、2000/2001 字符边界；验证未知 `type` 返回协议错误。

**通过标准**：`cjpm build` 通过，协议测试全部通过；超限只关闭当前连接，不能使进程退出。**证据**：构建输出、测试报告和超限/畸形输入样例。此阶段仍不要求账号或聊天可用。

## M2：账号与登录

**前置数据**：服务端本机准备 `alice`、`bob`、`charlie` 三个独立课堂测试账号。

**检查步骤**

1. 停止服务端后执行账号 `add/list/reset/disable`；`list` 只显示用户名和状态，命令行历史不含密码。
2. 重启服务端，确认账号仍存在；用正确、错误和已禁用账号分别登录，验证成功响应与错误响应。
3. 两个客户端登录，自动进入 `general`；重复登录同一账号，新连接生效、旧连接关闭，旧连接清理不删新连接。
4. 模拟账号文件缺失、损坏、无法读取；确认服务端给出明确错误并拒绝使用不完整账号状态。

**通过标准**：R1、R2 通过，账号文件无明文密码；停服管理与重启生效的规则得到验证。**证据**：匿名化后的账号文件结构、管理命令输出、登录/拒绝和重复登录的客户端记录。

## M3：公共聊天与私信

**检查步骤**

1. `alice`、`bob`、`charlie` 同时登录；`/who` 返回三人。`alice` 发一条公共消息，三人各收到一份。
2. `alice` 用 `/msg bob 你好` 发私信；`alice` 和 `bob` 各看到一份，`charlie` 看不到；给自己发私信只回显一份。
3. 向离线账号发送私信得到 `1005`；未登录连接试发公共消息或私信得到 `1001`。
4. `bob` 正常退出、突然断开及重复登录后断开旧连接；在线名单及时更新，其余客户端继续通信。

**通过标准**：R3–R6 通过，服务端生成的发送者身份不能被客户端伪造。**证据**：三客户端同步日志、服务端连接与清理日志、私信第三人未收到的记录。

## M4：健壮性、局域网演示与交付

**检查步骤**

1. 连续快速发送、畸形 JSON、超长帧、错误字段类型、慢客户端和异常断线各测一次；故障只影响对应连接，其余客户端仍可聊天。
2. 运行 `cjpm build`、`cjpm test`；按项目规范完成格式化、静态检查和另一名组员的代码评审。检查共享状态持锁、写 socket 加会话锁、状态锁内无阻塞 I/O。
3. 一台服务端和至少两台客户端在同一局域网完成登录、`/who`、公共消息、私信、断线与重新登录演示；记录主机 IP、端口、防火墙和 WiFi 客户端隔离配置。
4. 复查 README 的运行步骤与实际命令一致，报告说明明文 TCP、无离线消息和未完成扩展。

**通过标准**：R7、R8 通过，测试无失败，三机演示完成，交付文档与代码行为一致。**证据**：构建与测试结果、评审记录、三机演示记录和最终问题清单。若没有三台机器，阶段标为“阻塞”并记录原因，不以单机测试代替。

## M5：文件和图片传输（选做）

只有 M4 通过后才开始。至少验证接收者可接受/拒绝、完整文件与图片摘要一致、超过大小上限被拒绝、同名文件不覆盖、路径穿越被拒绝、中途断线清理临时文件、第三人收不到私有文件。若只提交扩展设计，不标记为传输功能通过，也不影响 R1–R8 的核心验收。

# 系统实现流程

> 面向项目组的端到端实现工作流：从环境准备到发布。每个阶段都有明确入口条件、
> 动作与出口标准（Gate）。

## 1. 总流程

```
P0 环境准备 ─► P1 协议冻结 ─► P2 最小系统 ─► P3 增量迭代 ─► P4 测试加固 ─► P5 发布交付
                    ▲                              │
                    └──────── 协议变更回环 ─────────┘
```

| 阶段 | 入口条件 | 出口标准（Gate） |
|---|---|---|
| P0 环境准备 | 代码仓库就绪 | `cjc/cjpm` 可用，官方示例跑通，stdx 路径确认 |
| P1 协议冻结 | P0 通过 | `DEVELOPMENT.md` §5 与 `protocol.cj` 一致，单测通过 |
| P2 最小系统 | P1 通过 | 最小系统 DoD 全部满足（见 `MINIMAL_IMPLEMENTATION.md`） |
| P3 增量迭代 | P2 通过 | I1–I3 各自验收通过 |
| P4 测试加固 | P3 通过 | 单测/集成/验收清单全部通过 |
| P5 发布交付 | P4 通过 | 三机联调通过，README 可复现，版本打标签 |

## 2. P0 环境准备

1. 安装仓颉工具链（官方 Windows 指引，含 VS 生成工具）。
2. 验证：`cjc --version`、`cjpm --version`。
3. 配置 stdx 依赖（net / encoding.json），确认导入路径。
4. 跑通官方 TCP 与 JSON 示例。
5. 记录版本信息到 `DEVELOPMENT.md` / `README.md`。

**Gate-0**：示例程序能编译、运行、收发一行数据。

## 3. P1 协议冻结

1. 依据 `DEVELOPMENT.md` §5 核对 `protocol.cj` 常量与字段。
2. 实现并单测 `encode`/`decode`/`readLine`/`writeLine`。
3. 实现字段校验函数并单测。
4. 冻结消息类型与错误码；后续变更走“协议变更回环”。

**协议变更回环**：

```
发现协议问题 ─► 更新 DEVELOPMENT.md §5 ─► 评审确认 ─► 修改 protocol.cj ─► 更新测试
```

**Gate-1**：协议单测（UT-01~04、UT-07、UT-08）全部通过。

## 4. P2 最小系统

按 `MINIMAL_IMPLEMENTATION.md` §5 的 S1–S6 执行。要点：

1. 先让服务端能 accept、逐行读、回显。
2. 再做注册/登录闭环。
3. 最后做单房间群聊广播与客户端显示。

**Gate-2**：最小系统 DoD 全部满足，两个终端能互聊。

## 5. P3 增量迭代

对每个迭代（I1/I2/I3）执行统一的功能实现循环：

```
1) 读需求与协议          → 明确输入/输出/错误
2) 更新/确认协议         → DEVELOPMENT.md §5
3) 改 protocol.cj        → 常量、辅助函数
4) 实现服务端            → handler + 不变量维护
5) 实现客户端            → 命令 + 显示
6) 写/更新测试           → 单测 + 集成用例
7) 本地联调              → 多终端
8) cjfmt / cjlint / test → 质量门
9) 提交 + 评审           → 合并
```

**Gate-3**：每个迭代的需求追踪项（见 `IMPLEMENTATION_PLAN.md` §6）验收通过。

## 6. P4 测试加固

1. 补齐单元测试（编解码、校验、哈希、房间逻辑）。
2. 跑通集成用例 IT-01~IT-09。
3. 执行验收清单（`DEVELOPMENT_TESTING.md` §6）。
4. 修复缺陷并回归。

**Gate-4**：`cjpm test` 全绿；验收清单无未通过项。

## 7. P5 发布交付

1. 更新 README 与部署说明。
2. 三台电脑同一 WiFi 实测（注册/登录/群聊/私聊/断线/心跳）。
3. 版本号与标签：`git tag -a v1.0.0 -m "LAN Chat v1.0.0"`。
4. 归档可执行产物与运行说明。

**Gate-5**：三机联调通过，按 README 可从零复现。

## 8. 日常开发工作流

### 8.1 分支

| 分支 | 用途 |
|---|---|
| `main` | 始终可编译、测试通过 |
| `feature/*` | 功能开发 |
| `fix/*` | 缺陷修复 |
| `docs/*` | 文档 |

### 8.2 提交

`<type>(<scope>): <subject>`，type ∈ {feat, fix, docs, refactor, test, chore}。

### 8.3 质量门（每次提交前）

```powershell
cjfmt -w src
cjlint src
cjpm build
cjpm test
```

## 9. 调试流程

| 症状 | 排查顺序 |
|---|---|
| 连不上 | 服务端是否启动 → IP/端口 → 防火墙 → 是否同 WiFi/同网段 |
| 收不到消息 | 是否已 join → 服务端广播日志 → 客户端读线程是否存活 |
| 消息乱/截断 | 是否按 `\n` 分帧 → 是否处理超长行 → UTF-8 边界 |
| 卡死 | 是否持锁做 I/O → 是否存在锁顺序反转 → 是否有未解锁路径 |
| 崩溃 | 保留异常堆栈 → 定位到具体 handler → 补输入校验 |

## 10. 评审要点（合并前）

- 协议文档与 `protocol.cj` 一致
- 共享状态访问均持 `gLock`
- socket 写均持 `writeLock`
- 锁顺序为 `gLock → writeLock`，且锁内无阻塞 I/O
- 输入按 §5.9 校验，错误码正确
- 无明文密码、无敏感日志
- 通过 `cjfmt` / `cjlint` / `cjpm test`

## 11. 角色与职责（建议）

| 角色 | 职责 |
|---|---|
| 负责人 | 协议冻结、Gate 评审、发布 |
| 服务端开发 | `server.cj`、并发与不变量 |
| 客户端开发 | `client.cj`、命令与显示 |
| 测试 | 单测/集成/验收执行 |
| 全体 | 代码评审、联调、文档同步 |
